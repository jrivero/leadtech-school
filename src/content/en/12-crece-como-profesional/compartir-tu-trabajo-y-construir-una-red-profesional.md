## Share evidence, not a promise

A portfolio does not need to be large or have a sophisticated website. Its purpose is to help another person understand what you built, what decisions you made, and what you learned. You can show a repository, a simple demo, or a reflection with screenshots and test steps. If you are not ready to publish code, prepare those materials in a local folder and share only what you feel comfortable sharing.

Choose a small project whose scope you can explain. For example, a task organizer that saves sample data in the browser. If it has no server, real users, or remote persistence, say so clearly: it is a local prototype, not an application ready for production. Explaining a limitation shows judgment; presenting it as a complete feature creates the wrong expectations.

## Make the project easy to understand

Add a README or equivalent note with these sections:

- **What problem it explores:** one or two sentences about the need and the intended users.
- **What it includes:** completed features and, if applicable, what is out of scope.
- **How to test it:** requirements, startup steps, and a short walkthrough that can be repeated.
- **Decisions:** one technical choice you made and why, without turning it into a universal rule.
- **Checks:** tests run and observed results. Do not say “tested” if you only opened the screen.
- **Limitations and next step:** a known bug, a question, or a specific improvement.

You can revisit one of the previous block's projects and make the path from need to implementation to verification visible. If you used AI assistance, distinguish the suggestion you received, the decision you made, and the tests you ran; do not consider code verified merely because it was generated. For example, in a document-question demo, show where an excerpt came from and what happens when there is not enough evidence. That way, the portfolio shows not just a screen, but also your judgment about quality and security.

Include an image or demo only if it helps explain the behavior. Check that links work and that alt text describes important images. Before sharing, look for keys, tokens, private addresses, personal data, and files that should not be public. Use fictional information in example screenshots. If you use a hosted repository, review its visibility settings; GitHub's documentation explains how the profile README works, but you do not need to make your profile public to complete this practice.

## Share to start a conversation

A useful invitation presents the project in a few lines: what it is, which part you want to show, and what feedback would help. For example: “I created a task-list prototype to practice filters. Could you try the README steps and tell me whether it is clear how to mark a task as complete?” That request is easier to answer than “What do you think of everything?”

Building a professional network does not mean sending the same message to many people. Start in spaces where you can participate respectfully: a technical community, a peer review, a local meetup, or a collaborative project. Read the rules, contribute a specific question, and offer useful feedback when you have relevant knowledge. If someone helps you, thank them for their time and say what you changed afterward.

Do not assume every conversation will turn into a collaboration, referral, or job. Sharing your work can help you learn, but it does not guarantee a response or a professional outcome. The immediate value is practicing how to explain your work, listen to an observation, and decide whether to incorporate it.

## Verifiable practice

Choose one of these three outputs: a repository with a README, a demo with instructions, or a written reflection on a project. Complete the sections above with accurate details about your process. Include a limitation that still exists and a screenshot or reproducible example if it adds clarity.

Finally, share the sample with someone you trust or review it aloud as if that person did not know the project. Write down a specific question to get feedback and record the answer—or, if you do not have one yet, the question that remains open. The practice is complete when there is an understandable sample and you can explain what you did without taking credit for someone else's work or hiding what is unfinished.
