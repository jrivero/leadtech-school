## Verification needs an independent reference

Code generated by an agent should be reviewed like any new code, and the process must also be checked for compliance with the authorized scope. Start with a source outside the agent's response: a requirement, accepted example, contract, or test written before examining the solution. If the same agent invents the behavior, implements the change, and then writes tests that only confirm its own interpretation, the cycle may be consistent and still be wrong.

Break verification into questions: What behavior does the person observe? Which boundary inputs change the rule? Which paths were modified? Which dependencies or permissions appeared? What data could leave the environment? Examine the complete diff, including hidden files, configuration, scripts, and documentation. Look for network operations, access to secrets, permission changes, and tests that were removed or weakened. Do not run an instruction suggested by the agent if you do not understand what it changes.

Test the critical path first, then boundaries and failures. Run existing tests to detect regressions, analyze new ones to check that they really fail when the defect is present, and verify the build or types if the project already offers those checks. A screenshot or visual demo may show one state; it does not reveal every branch. If the task affects security, payments, data, or production, require appropriate controls and review by an authorized person. Do not accept a deployment as a way to “see if it works.”

## Example of a simple rule

A list displays tasks numbered from one, but Python indexes from zero. The agent must implement `obtener_tarea(tareas, numero)`, which returns the task for a valid number and a controlled result if the number is zero, negative, or greater than the list length. Before reviewing the code, define four cases: first task, last task, zero, and a number greater than the total. Independent verification compares each output with the specification; it does not need to call a service or use real data.

The agent's summary might say “all tests pass.” Check which command was run, whether its exit code indicated success, and whether the tests include all four cases. Also inspect that the number is converted only once and that no path ends by showing an unhandled exception to the user. If you cannot reproduce the environment, mark the check as unverified and request a reproducible run.

## Step-by-step activity

1. Write a one-sentence assignment for the numbering rule and add valid inputs, boundaries, and the expected error result.
2. Ask the agent for a plan before allowing changes. Confirm that the one-based/zero-based conversion is clear.
3. When there is a proposal, review the changed files and look for out-of-scope changes, new dependencies, and access to the network or secrets.
4. Run cases you prepared yourself, not only those proposed by the agent. Include zero, first item, last item, and out of range.
5. Run the relevant project checks; record their names, results, and limitations without copying sensitive data.
6. Make a small diff, repeat the cases, and explicitly decide whether to integrate or return the work for changes.

## Verification and solution

For a list of three items, `1` should select the first and `3` the last; `0` and `4` should be rejected without changing the collection or showing an unhandled exception. These four cases are a starting point, not proof for an empty list, a non-integer type, or another requirement. If empty-list behavior matters, add that case according to the contract. The solution is supported when the results match and the diff contains no unauthorized side effects.

The evidence should distinguish “the test passed locally,” “the diff was read,” and “a test was proposed but not yet run.” Avoid absolute statements such as “the agent guaranteed it is safe.” If there is an environment limitation, unavailable dependency, or product question, keep it visible before integration.

## Common mistakes

- **Reviewing only the final explanation.** Inspect code and configuration, not just the summary.
- **Accepting tests based on an unapproved assumption.** Compare each expectation with the independent requirement.
- **Allowing the agent to run destructive commands or deploy.** Restrict tools and require approval for external effects.
- **Confusing the absence of a failure with sufficient proof.** Add relevant negative paths and boundaries.
- **Writing “verified” as a courtesy.** Record exactly what ran, in which environment, and what remains pending.

## Summary

Verifying an agent's work means comparing it with independent requirements, inspecting the entire diff, and running your own checks. Review permissions, dependencies, errors, and boundaries, and document the evidence and uncertainties. Automation can speed up a change, but responsible integration and acceptance still require human judgment.
