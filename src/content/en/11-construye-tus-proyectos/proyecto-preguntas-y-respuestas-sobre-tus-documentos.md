## Project brief

This practice continues the work on requirements and fundamentals: it is not enough to ask for “an AI that knows my documents”; define which questions it covers, what evidence it must show, and when it abstains. The project connects implementation with quality and security through a local collection, non-sensitive data, and a repeatable evaluation that you can also document in your portfolio.

Build a small tool that lets people ask questions about a limited set of documents and returns relevant passages with the file name. The goal is not to create a customer-ready product, but to visibly check what data the system finds and what it can claim based on that data.

RAG stands for retrieval-augmented generation. A RAG system has two separate tasks: a retriever locates useful passages in a collection, and a generator uses those passages and the question to draft an answer. Retrieval selects evidence; generation creates new wording. If your program only ranks passages and prints them, you have demonstrated search and retrieval, not generation with a model. This distinction prevents presenting a simple search as if it were a generative assistant.

## Minimum scope

Work with three to five text or Markdown documents that are public or invented for the exercise. Support only those formats; leave out PDFs, users, permissions, deployment, the Internet, and external databases. Split the texts into paragraphs or short blocks, keep the file name, and calculate which ones are most similar to the query. The first version can score matching words with a simple formula such as TF-IDF, without installing packages or creating an API key.

The initial response should show up to three literal passages, their file, and a notice when there is not enough evidence. It is an extractive demo: it does not summarize, infer, or invent a new sentence. You can run the prototype from the terminal with a query such as `python3 consulta.py "¿Qué plazo indica el documento?"`.

## Step-by-step plan

1. **Prepare safe data.** Create a `documentos/` folder with short example texts. Do not use customer histories, real contracts, or personal information.
2. **Define the passage format.** For each block, store its text, source file, and index. Use small blocks that keep an idea and its context together; try two sizes instead of assuming one is perfect.
3. **Implement retrieval.** Using Python's standard library, read files, normalize capitalization and punctuation, tokenize, and calculate a score between each passage and the query. Sort the results and discard empty matches.
4. **Expose evidence.** Print the passage, file name, and an understandable score. Add a configurable minimum threshold: when nothing exceeds it, respond that there is not enough data.
5. **Test varied cases.** Write at least five questions whose answers are in the documents and three that cannot be answered. Record which passage should appear and what happened.
6. **Document how to repeat it.** In a `README`, state the Python version, expected structure, run command, limitations, and example queries.

## Deliverables and acceptance

Submit `consulta.py`, the folder with test documents, a `README`, and an evaluation table with the question, expected evidence, retrieved result, and verdict. The practice is accepted if it works offline and without keys, shows a source for every result, finds relevant evidence in positive cases, and abstains in negative cases. Also check an empty folder and a question made only of spaces; neither should cause an error or produce a misleading answer.

## Suggested solution and common errors

A clear solution can separate four functions: read files, split texts, score, and present results. To score, compare the question terms with each passage and reduce the weight of words that appear in every document. Always keep the original reference with the text; do not try to reconstruct it after sorting. If the result only shows passages, describe it as extractive retrieval.

As an optional extension, add a model that runs on your machine with Ollama: first retrieve the passages, then send only those passages and the question to the local endpoint `http://localhost:11434/api/chat`. In the instruction, ask it to answer only from the context and acknowledge when evidence is missing; show the sources alongside the answer. That second stage does add generation, although it can be wrong and needs its own evaluation. Do not use a remote endpoint or paid API for this exercise; before downloading a model, check its license and whether your machine can run it.

Common mistakes include passages that are so large they mix topics, confusing a high score with certainty, omitting the source, failing to test unanswerable queries, and sending private data to an external service. Keep a small collection and measure retrieval first: a generator cannot fix irrelevant evidence.
